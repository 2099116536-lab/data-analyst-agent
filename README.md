# Data Analyst Agent · NL2SQL 数据分析 Agent

把一句中文业务问题变成 SQL，跑出结果，给结论、给图表，并且在答不了的时候老实说"答不了"。

**技术栈**：Python（标准库）· SQLite · 自研状态机 · 可选 DeepSeek / OpenAI
**零第三方依赖**：评测、单测、CLI 全部用标准库跑通（`pip install` 只为了开 HTTP 接口）

```
问题 → 意图路由 → Schema 检索 → 生成 SQL → EXPLAIN 校验 → 执行 → 结果自检 ─┬→ 结论 → 图表
                    ↑                                          │
                    └────────── 修复（≤2 轮）←──────────────────┘
```

## 快速开始

```bash
python data/make_db.py          # 生成示例库（4000 单 / 8007 明细，固定种子可复现）
python main.py ask "各城市的销售额是多少？"
python main.py eval             # 全量评测（有 key 走 LLM，没有走规则基线）
python main.py eval --no-llm    # 只跑规则基线，任何环境都能跑
python -m unittest discover -s tests -v   # 22 个单测
```

```
$ python main.py ask "各城市的销售额是多少？"

SELECT c.city, ROUND(SUM(oi.amount),2) AS gmv
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status IN ('已支付','已完成')
GROUP BY c.city
ORDER BY 2 DESC

city  gmv
----  ------------
西安  733,348.71
成都  729,232.24
...
结论：10 个分组，西安 最高：733,348.71，占总量的 12.2%；第二是 成都（729,232.24）。
耗时：route 0.8ms → retrieve 0.1ms → generate 2.9ms → validate 0.4ms → execute 1.7ms
```

## 评测：规则基线与 LLM 的正面比较

评测口径是**执行结果比对**（比对结果指纹，不比对 SQL 文本），避免"写法不同但答案一样"被误判。
数据集四段：`dev`（22 条，写规则时参考）→ `holdout`（8 条，换表述）→ `unseen`（8 条，写完规则才看到）→ `boundary`（6 条，本 Agent 不该答的题）。

| 路径 | dev | holdout | unseen | boundary | 延迟 avg / p95 |
|---|---|---|---|---|---|
| 规则编译器（`--no-llm`） | 22/22 · **100%** | 8/8 · **100%** | 1/8 · **12.5%** | 6/6 · **100%** | **3.4 / 6.5 ms** |
| DeepSeek（`deepseek-chat`） | 22/22 · **100%** | 8/8 · **100%** | 6/8 · **75.0%** | 6/6 · **100%** | 914 / 1539 ms |

指标说明

| 指标 | 值 | 口径 |
|---|---|---|
| Schema 检索省下的提示长度 | **54.8%** | 全量 schema 891 字符 → 按问题召回后平均 402 字符 |
| 表命中率 | 100%（规则）/ 97.2%（LLM） | Schema 召回到的表是否覆盖标准答案需要的表 |
| 边界识别率 | **100%** | 预测/归因/多指标/大区粒度/跨年对比，应识别为"答不了" |

**这张表就是项目的核心结论**：规则基线在见过的问法上完美且快 270 倍，但未见过表述掉到 12.5%；
LLM 泛化到 75%，但慢 270 倍、偶发口径偏差。所以线上正确做法不是二选一 ——
**LLM 生成 + 规则口径校验 + 规则兜底**。

诚实的读法：

- `dev` 100% 不证明能力，它就是需求清单，规则是针对它写的；
- `holdout` 首跑只有 **2/8**，我按失败原因补了 6 处表述覆盖才到 8/8（详见下面的 BAD CASE）；
- `unseen` 是唯一没被改过的数字，**12.5% 才是规则基线的真实泛化水平**，别拿 100% 当卖点。

## 关键设计决策

**1. 先判"能不能答"，再判"怎么答"**
预测（"下个月会卖多少"）、归因（"为什么下降"）、多指标并列、大区粒度（库里只有城市）这四类问题，
直接返回澄清而不是硬生成 SQL。数据分析场景里**答错比不答代价大**——一条口径错的 SQL 会被人当真用。

**2. 口径写进代码，不交给模型**
"销售额只算已支付+已完成"这类口径固化在 system prompt 和规则里。模型负责把自然语言翻成结构，
不负责定义业务口径。

**3. 基准日期从数据里取，不用 `date('now')`**
库里最新订单日是 2026-11-01，而系统时间是 2026-11-02。模型默认会写 `date('now')`，
"最近 30 天"就差一天，评测表现为"SQL 能跑但结果对不上"。改成把 `as_of` 注入 prompt 并写死日期常量。
**这是本项目最值钱的一个坑**，因为它在真实生产里同样会发生（数据延迟、时区、快照库）。

**4. 校验前置到执行之前**
`EXPLAIN` 预检能挡住列名/表名错误，不用等执行失败再修。修复最多 2 轮，仍失败就把失败 SQL 一起返回。

**5. Schema 检索而不是全量塞**
按关键词给 4 张表打分，只把命中的 1-2 张表 + 相关指标口径放进 prompt，省 54.8% 的提示长度，
表命中率不降。这个收益在表多的时候（几十张表）会从"省钱"变成"能不能用"。

## BAD CASE 记录（都是真踩的）

| 现象 | 根因 | 修法 |
|---|---|---|
| `holdout` 首跑 2/8：6 条问法全错 | 规则是模板匹配，"卖了多少钱"同时命中 `gmv` 和 `qty`，SELECT 出两列；"最低的3个" 只认 "最高的"；"黑卡用户" 没命中等级过滤；"每天" 没实现 | 指标改互斥 + 补同义表述 + 补 `date` 维度。修完 8/8，但这属于"见过答案后的修"，不算泛化 |
| "最近30天" 结果差一天 | 模型写 `date('now')`，与数据截止日错位 | 注入 `as_of`，prompt 里禁止 `date('now')`；同时统一"含基准日"口径（11-01 往前 30 天 = 10-03） |
| `u02`「成都和重庆哪个卖得更好」生成 0 行 | 模型把"城市"理解成 `channel`，SQL 能跑但筛出空集 | 保留为已知失败：单条问题里的多值对比（"A 和 B 哪个好"）需要专门的对比模板，当前未支持 |
| `u07`「各品类的销量占比」判失败 | 模型输出了 3 列（品类/销量/占比），标准答案 2 列，指纹比对按列数严格判定 | 属于**评测口径**的局限：模型其实答得更全。后续改成"标准答案列是生成结果的子集即算过" |

## 目录

```
data/make_db.py      造数（4000 单 / 8007 明细，固定 seed）
data/schema.json     表结构 + 指标口径 + 库外主题（Agent 拒答依据）
src/db.py            只读护栏 / EXPLAIN 预检 / 结果指纹
src/schema.py        Schema 检索（省 54.8% 提示长度）
src/compiler.py      规则式 NL→SQL（离线基线）
src/agent.py         状态机：路由→检索→生成→校验→执行→自检→修复→结论→图表
src/llm.py           LLM SQL 生成（标准库 urllib 调 OpenAI 兼容接口）
src/chart.py         终端表格 + ECharts option
src/eval.py          执行准确率 / 表命中 / 边界识别 / 延迟分位
eval/*.jsonl         44 条评测集（dev 22 / holdout 8 / unseen 8 / boundary 6）
eval/results_*.json  两条路径的完整评测明细（可复现）
tests/               22 个单测（标准库 unittest）
server.py            POST /ask（FastAPI，缺依赖自动降级到 http.server）
```

## 已知局限

1. **只支持单指标**：一次问两个指标会被判为"需要澄清"，因为指标口径不同不能混在一张表里。
2. **不做预测/归因**：这两类需要时间序列模型或实验对照数据，当前只有流水表。
3. **规则基线的 12.5% 是真实上限**：换库、换行业、换说法都要求重新写模板，这也是必须接 LLM 的原因。
4. **评测集 44 条偏小**：够发现口径错误，不够刻画分布；`u07` 这类判定歧义说明评测本身也需要迭代。
